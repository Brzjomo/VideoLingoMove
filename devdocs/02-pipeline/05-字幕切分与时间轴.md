# 字幕切分、润色与时间轴对齐（step5 / step5.2 / step6）

## 一、职责与边界

step5 把「句子级」的双语行按长度上限再切碎成「字幕级」；step5.2 是它之后**可选**的一步（默认关），逐行润色译文**措辞**；step6 用 word 级时间戳给每一行字幕重新分配起止时间并写出 SRT。

- **负责**：① step5 `split_for_sub_main` 判定哪些行超长（2026-09-20 起长度上限由 `core/subtitle_limits.py` 解析：**打开「按语言自动设置」时源/译两侧各按自己语言的档位**，关闭时退回旧行为——源文按字符数、译文按加权长度 × `target_multiplier`），按「纯本地 / 机械等分 / LLM 对齐」三条分支把一行拆成 2 段并对齐译文（LLM 结果先过对齐校验；连续失败退回机械等分），最多重试 3 轮，再把**极短字幕并入相邻条**并打印一行对齐自检，产出 `output/log/translation_results_for_subtitles.xlsx`；② step5.2 `polish_subs_main`（**可选，默认关**，开关 `subtitle.polish_translation`）把上一步的表按 `BATCH_SIZE = 20` 行一批交给 LLM 润色措辞（逐行对应、不许增删信息；**是否允许思考、只润色哪些行**由同一天新增的 `subtitle.polish_thinking` / `subtitle.polish_long_lines_only` 决定 —— 注意"允许思考"只管润色调用，见 §5.2），逐行过 `core/subtitle_split.polish_ok`，对改动过的行再做一次批量审校：护栏不过的行**保持原译文**、审校判为"改了信息"的行**回退原译文**，产出 `output/log/translation_results_polished.xlsx`（行数与 `Source` 都与 step5 产物逐行一致）；③ step6 `align_timestamp` 把句子文本沿 word 级时间戳做**单调子串匹配**（精确匹配失败时按 `subtitle.align_on_mismatch` 决定「模糊兜底并告警」还是「抛错」），得到 `(start, end)` 与 `duration`，缝合 <1 秒的空隙，格式化 SRT 时间戳，按 `for_display` 处理标点（`polish_translation_for_display`：**仅非 CJK 目标语**把译文 `，。` 换成空格，CJK 保留句中逗号）、剥掉原文/译文的**行尾**句末标点（`subtitle.strip_punctuation_in_source` 额外去原文标点），并按 4 种列组合写出 `output/src.srt`、`trans.srt`、`src_trans.srt`、`trans_src.srt`；④ `core/json_to_subtitle.py` 作为旁路工具，把 ASR 的 JSON 直接转成 SRT 与 `cleaned_chunks.xlsx`。
- **不负责**：step5 **不写任何 SRT**（这是常见误解，见 5.1）；step6 **不写** `output/audio/*_subs_for_audio.srt`（那套配置已随配音链路删除，符号与调用点都已清理，仅 `core/step4_2_translate_all.py` 里留了一个不落盘的占位文件名）；step5.2 **不改行数、不改 `Source`、不碰时间轴**（只替换 `Translation` 文本），也不写任何 SRT；开关关着时它**一次 LLM 调用都不发**（只打印一行跳过）。字幕烧录在 step7。

## 四、关键数据结构

### 4.1 三次时间映射（Word 级 → sentence 级 → subtitle 级）

| 层级 | 载体文件 | 字段 | 类型 / 单位 | 产生者 |
| --- | --- | --- | --- | --- |
| ① Word 级 | `output/log/cleaned_chunks.xlsx` | `text`, `start`, `end` | `text` 为带双引号的 word 字符串；`start`/`end` 为 float **秒** | step2 `whisperX_utils.save_results`（`core/all_whisper_methods/whisperX_utils.py`）或 `json_to_subtitle.generate_excel_from_segments` |
| ② Sentence 级 | `output/log/translation_results.xlsx` | `Source`, `Translation`, `timestamp`, `duration` | `timestamp` 是 `HH:MM:SS,mmm --> HH:MM:SS,mmm` **字符串**；`duration` 为 float **秒** | step4.2 `translate_all`（`core/step4_2_translate_all.py`） |
| ③ Subtitle 级 | `output/log/translation_results_for_subtitles.xlsx`（step5.2 打开时 step6 改用 `output/log/translation_results_polished.xlsx`）→ `output/*.srt` | `Source`, `Translation`；SRT 的序号/时间行/文本行 | 时间轴继承自 ②，按切分后**逐行重算**（行数变多，时间被重新分配） | step5 →（step5.2，可选）→ step6 |

映射规则：①→② 由 `get_sentence_timestamps` 把「句子文本」在「word 拼接串」中子串匹配，取首词 `start` 与末词 `end`；②→③ 由 step5 在一行内部插 `\n` 拆成多行，**拼接文本不变**，所以 step6 重跑同一套匹配即可把时间重新分配到更细的粒度。step5.2 若打开，只在 ③ 上**替换 `Translation` 文本**（行数与 `Source` 两列都不动），因此不触及 ②→③ 映射的前提。

实测对照（示例数据，非推断）：`output/log/cleaned_chunks.xlsx` 当前为 23000 个 word 行、列为 `text`/`start`/`end`，中文逐字且带双引号（如 `"那"`）。

### 4.2 SRT 文本结构

`generate_subtitle_string`（`core/step6_generate_final_timeline.py`，定义在 `align_timestamp` 内部）逐行拼接：

```text
{i+1}
{row['timestamp']}
{line1}
{line2}

```

- `columns` 只有 1 列时只写 `line1` 再补一个 `\n\n`，**不再产生空的第二行**（历史缺陷 P3-9 已修）；`src.srt` / `trans.srt` 与 `src_trans.srt` / `trans_src.srt` 的块间都恰好是 1 个空行。
- 文本中的连续空白会被压成单个空格（、）。
- 整个字符串最后 `.strip`，因此文件末尾没有多余空行。

### 5.1 `core/step5_splitforsub.py`

| --- | --- | --- | --- |

| `row_overflows(src, tr, limits)` | `(str, str, SubtitleLimits) -> bool` | 任一侧超过**它自己那一侧**的上限（含宽容量 `GRACE = 1.15`）就返回 `True` | 纯函数 |
| `align_subs(src_sub, tr_sub, src_part)` | `(str, str, str) -> (list[str], list[str], str)` | ① `_bump_align_stat("rows")`；② 取一次 `_align_validation_enabled()`（`subtitle.align_validate`）与 `_align_rewrite_allowed()`（`subtitle.align_allow_rewrite`，两者缺键/读失败都视为**开**）；③ `get_align_prompt(src_sub, tr_sub, src_part)`（第 3 条按 `config_utils.align_allow_rewrite()` 取轻改写/严格两版）+ `ask_gpt(response_json=True, valid_def=valid_align, log_title='align_subs')`；④ `src_parts = src_part.split('\n')`、`tr_parts = [item[f'target_part_{i+1}'].strip() …]`，再用 `get_joiner(language)` 拼出 `tr_remerged`；⑤ 拼接与整句译文**不等**时记 `rewritten` 并把 `Table` 标题改成「🔗 Aligned parts（含轻改写，已过重复/漏译校验）」 | 网络请求；LLM 少返回一项 → `KeyError: 'target_part_N'`（由 `split_align_subs` 捕获后降级为机械等分） |

| `split_align_subs(src_lines, tr_lines, limits=None)` | `(list[str], list[str], SubtitleLimits=None) -> (list[str], list[str], list[str])` | ① 解析长度限制（`limits` 或缺省 `resolve_limits()`：自动档位 = 两侧各按自己语言；手动 = 旧的字符/加权×multiplier）；② 判定 `identical_src_trans = src_lines == tr_lines` 与 `use_llm = use_llm_sentence_split`；③ 逐行 `row_overflows`（任一侧超**自己那侧**的上限）命中者记入 `to_split`；④ 线程池并发执行 `process(i)`；⑤ **出口不变量**：任一侧段数不等或为空 → 该行保留原样并告警；⑥ 展平两个列表 | 就地修改传入的 list；`process` 内的异常被 `try/except` 捕获后只打印告警并**保留原始行** |

| `reset_align_stats()` / `align_stats_summary()` | `() -> None` / `() -> str` | 模块级 `_ALIGN_STATS`（`rows` / `rewritten` / `rejected` / `fallback`，`threading.Lock` 保护，因为 `process` 是多线程）+ 最多 5 条失败原因。汇总文案固定为 `📊 对齐统计：LLM 对齐 N 行，其中轻改写 X 行 / 校验拦下 Y 次（带原因重试）/ 退回机械切分 Z 行`，再附「原因示例：…」（最多 3 条）；`rewritten`/`rejected`/`fallback` **全为 0 时返回空串**（正常片子不打印噪音） | 模块级可变状态；`split_for_sub_main` 每次开头 `reset_align_stats()` |

**`process(i)` 的三条切分分支**

| 条件 | 行为 |
| --- | --- |
| `not use_llm`（仅转录模式下关掉了断句优化） | 段数由 `subtitle_limits.parts_needed(measure_for(src, limits), calc_len(tr), limits)` 算出（两侧各按自己档位，夹在 1~3）；源文交给 `subtitle_split.split_at_boundaries(src, need, window=_boundary_window(), language=get_source_language())` —— **按句法边界切**（硬边界「。！？；：!?;:…、，」→ 日语接续/助词 → 拉丁连接词），窗口内找不到边界才退回理想宽度位置；译文用 `split_text_evenly` 等分成同样段数；`split_text_evenly` 返回 `None`（译文太短切不出恰好 n 段）则**抛异常让本行整行保留** —— 零 LLM 调用。⚠️ 2026-09-20 之前这里调的是 `split_by_punctuation`（`core/step3_2_splitbymeaning.py`），**现在 step5 已不再使用它** |
| `identical_src_trans`（直通模式，Source 与 Translation 是同一份文本） | 用 LLM 只切源文（`split_sentence(..., num_parts=2)`），译文按行数机械等分，省掉「让 LLM 把一段文本与它自己对-齐」的无谓调用 |
| 其余（正常翻译模式） | `split_sentence` 切源文 → `align_subs` 让 LLM 把译文对齐到这些切点；**`align_subs` 抛任何异常**（连续 3 次校验失败、网络失败、`KeyError`…）时退回 `split_text_evenly` 的**机械等分**，记一次 `fallback` 并打印 `⚠️ 第 {i} 行 LLM 对齐不可用（{异常类型}），已退回机械等分切分`；等分做不到"恰好 n 段"则重抛，由外层 `except` 打印告警并保留原行 |

三条分支都以 `eu.check_cancel` 开头：暂停时在该行阻塞、停止时抛 `StopTask`——没有这个钩子时「停止」在 step5 期间点了没有任何反应。

LLM 对齐的**失败/拦下→重试→等分**链条（`subtitle.align_validate` + `subtitle.align_allow_rewrite` 打开时的默认路径）：

```text
align_subs → valid_align 校验
   ├─ 通过             → 用 LLM 的切点；若拼接 ≠ 整句译文则计「轻改写」
   ├─ 不通过（附原因）  → ask_gpt 把原因回注给模型重试（同一 prompt，最多 3 次）→ 计「校验拦下」
   └─ 3 次仍不通过/网络异常 → split_text_evenly 机械等分 → 计「退回机械切分」
```

### 5.2 `core/step5_2_polish_subs.py`（step5.2 字幕润色，可选）

开关 `subtitle.polish_translation` **默认关**（判定点 `core/config_utils.polish_translation`：**缺键/读失败一律按关**，与 `align_allow_rewrite` 缺省按开正好相反 —— 老 config 不能因为读键失败就偷偷调 LLM）。它排在 step5 与 step6 之间，**只改措辞**：step5 的对齐按设计不许改写措辞（见 §7.7），所以「把句子改顺」只能发生在专门的一步里，且必须由用户显式打开（侧边栏「✨ 字幕润色（可选）」，见 §六）。

打开后还有**两个取舍开关**（都在同一个面板里、都在润色关着时置灰，判定点都在 `core/config_utils.py`）：

| 开关 | 默认 | 作用 | 判定点 / 缺键行为 |
| --- | --- | --- | --- |
| `subtitle.polish_thinking` | `true` | 润色时是否允许模型思考（**只管润色调用**；审校不跟随）。关掉 → `polish_lines` 的 `ask_gpt(..., extra_body={"thinking": {"type": "disabled"}})`，**并自动把覆盖率门槛换成 0.85** | `core/config_utils.polish_thinking`；**缺键/读失败按开**（老 config 保持"更忠实但贵"的旧行为） |
| `subtitle.polish_long_lines_only` | `false` | 只润色"有分句的长行"（宽度 ≥ 15 且含 `，、；：,;:` 之一），其余行**原样保留** | `core/config_utils.polish_long_lines_only`；缺键/读失败按关（= 全部行都润色） |

> 用户原话（2026-09-21）："加个支持关闭思考的开关，放在侧边栏润色开关的下方……再加个只润色有分句的长行的开关……这样可以按需选择更好的效果还是更低的花费。"

| `polish_lines(sources, translations, max_width=None, *, use_thinking=None, long_lines_only=False)` | `(Sequence[str], Sequence[str], Optional[float], *, Optional[bool], bool) -> (List[str], Dict[str, int])` | 见下方分批流程。三个取舍旋钮：① `max_width` = 目标语显示宽度上限（超了该行回退原译文）；② `use_thinking=None` 时现读 `core/config_utils.polish_thinking()`，**关思考 = 每次润色调用都带 `extra_body={"thinking": {"type": "disabled"}}`，且覆盖率门槛改用 `POLISH_COVERAGE_MIN_NO_THINKING = 0.85`（原来是 `POLISH_COVERAGE_MIN = 0.70`）**；③ `long_lines_only=True` 时先用 `subtitle_split.needs_polish_long_line` 预筛，只把"有分句的长行"送去润色，其余行**原样保留**。统计字典新增 `skipped`（预筛跳过）/ `sent`（实际送出）/ `thinking`（0/1）。返回列表的**长度恒等于输入**，任何失败都只把对应行**保持/回退成原译文**并计数（绝不丢内容） | 每批 `eu.check_cancel()`（暂停/停止在批次边界生效）；`ask_gpt(log_title=_log_title('polish_subs', extra_body), extra_body=extra_body)`（**关思考时带 `extra_body` 且落进 `polish_subs_nothink` 分区，开思考时传 `None` = 与旧行为完全一致**，`extra_body` **只由这一次调用携带**）与审校调用 `ask_gpt(log_title='polish_audit')`（**不带 `extra_body`**，恒按模型默认档） |

每批的处理链（`polish_lines`，逐批独立、互不影响）：

```text
预筛（long_lines_only 为真时）：targets = [i for i, text in enumerate(current)
                                            if subtitle_split.needs_polish_long_line(text)]
  → 跳过的行**原样保留**（不参与任何调用），stats['skipped'] / stats['sent'] 各记一笔；
    批次按 **targets** 切（跳过的行不占批），所以批数会变少
min_coverage = POLISH_COVERAGE_MIN (0.70) if use_thinking else POLISH_COVERAGE_MIN_NO_THINKING (0.85)
每 20 行一批：eu.check_cancel() → get_polish_prompt(rows, max_width)
             → ask_gpt(valid_polish, log_title=polish_subs / polish_subs_nothink, extra_body=…)
  ├─ 调用/解析失败（网络、JSON、id 对不上）→ 该批全部保持原译文，failed_batches += 1（继续下一批）
  └─ 成功 → 逐行 subtitle_split.polish_ok(原译文, 润色后, max_width=limits.tr_limit,
                                          min_coverage=min_coverage)
        ├─ 不通过 → 该行保持原译文，rejected += 1，原因进 stats['reasons']（最多留 5 条）
        └─ 通过   → 写入结果；**归一化文本与原译文不同**才进审校名单（2026-09-21 收紧：
                    刻意不看模型自报的 `changed` 标记 —— 它会虚报也会漏报；只丢行尾句号这类
                    纯标点差异不进名单，省一次白花钱；最终"改动行数"另行统计，见下）
最后对审校名单（非空时）做**一次**批量审校（分区恒为 polish_audit，不带 extra_body = 按模型默认档思考开）：
  ├─ 判定 info_changed → 该行回退原译文，reverted += 1
  └─ 审校不可用       → 改动全部按原样保留（audit_failed += 1）
最后一行由**最终文本**反推统计：
  stats['changed'] = sum(1 for before, after in zip(current, result) if str(before) != str(after))
  （= 用户肉眼所见的改动行数；被审校回退的行文本等于原译文，自然不计入，所以
    "改动/审校回退"是两个独立计数，改动里**不再**做 `changed -= 1` 这类扣减）
```

统计文案（`polish_stats_line`，`polish_subs_main` 末尾打印）：

```text
✨ 润色统计：N 行（送出 X / 预筛跳过 Y）分 M 批，改动 A 行 / 护栏拦下 B 行 / 审校回退 C 行 / 失败 D 批｜思考 开/关
   拦下原因示例：#7 dropped or changed number(s): 6；…（最多 3 条，原因文案来自 polish_ok，本身是英文）
```

### 5.4 `get_sentence_timestamps` 与 `_fuzzy_find` 的对齐算法

```text
输入：df_words = cleaned_chunks.xlsx（text/start/end，word 级）
 df_sentences = 待对齐的 DataFrame（列名必须是 'Source'，按 index 顺序遍历）
 on_mismatch = 'warn'（默认：模糊兜底 + 告警） | 'strict'（精确匹配失败即抛错）

① 构造全词串 full_words_str = concat( remove_punctuation(word.lower)) # :126-131
 同时建立 position_to_word_idx：每个字符位置 → 所属 word 的行号
 （word_idx_at(pos) 在越界时退到最近的已知位置，# :133-139）
② 逐句顺序扫描（current_pos 单调递增，不回溯，逐位比较） # :141-163
 clean_sentence = remove_punctuation(sentence.lower).replace(" ", "") # :143
 命中则取
 start = df_words['start'][首词行号]，end = df_words['end'][末词行号] # :149-155
 命中后 current_pos += sentence_len（保证句子与句子不重叠、保持音频顺序）
③ 未命中：
 - on_mismatch == 'strict' → 打印警告 + show_difference + raise ValueError # :165-169
 - 否则走 _fuzzy_find 兜底（# :172-191）：
 a. 用句子前缀在词串中 find（锚长 24/16/8/4 依次尝试），命中则按句子长度截一段
 b. 前缀找不到 → 取最长公共块，按块在句中的位置按比例外扩
 c. 仍失败（例如清洗后为空串）→ 沿用上一个词的结束时间，记为相似度 0
 兜底后 current_pos = max(current_pos, end_pos) # :190
④ 只要发生过兜底就打印「共 N/M 条字幕未精确匹配，已使用兜底对齐」与最多 10 条明细 # :193-200
```

关键约束（都是隐式契约）：

| 约束 | 依据 | 违反后果 |
| --- | --- | --- |
| 句子的归一化文本**应当**是全词串的**连续子串**，且**顺序与音频一致** | 单调扫描 | `strict` 下抛 `ValueError`、整个 step6 中断；`warn`（默认）下模糊兜底并告警，但**兜底前进的词位可能偏移，造成后续句子连锁失配** |
| 句子侧删掉了**所有空格**（`.replace(" ", "")`），word 侧只做首尾 `strip` | vs | 若某个 word token 内部含空格（例如没有词级时间戳时 `json_to_subtitle` 用整段文本兜底，`core/json_to_subtitle.py`），全词串会混入空格 → 位置错位甚至落到兜底路径 ⚠️ |
| `df_sentences` 必须按 0..n-1 的 RangeIndex 排列 | `.items` 与 current_pos 单调性 | 索引乱序 → 时间分配错乱 |
| 标点/大小写被归一化，但**字符本身**不能变 | | step5 的 LLM 若改写了源文（回填表里 `src_parts` 来自 `split_sentence`，不会改写；但人工编辑 xlsx 会）→ 触发兜底或抛错 |

## 七、技术要点与坑

### 7.1 `calc_len` 的权重（注释与实现现已一致）

`core/step5_splitforsub.py::calc_len` 现在只是 `core/subtitle_limits.measure(text, "width")` 的**同名包装**（"字幕长度"的度量只有一处定义），注释与实现都写 **中日 1.75、韩文 1.5、泰文 1、全角符号 1.75、其他 1**。⚠️ 历史文档里"注释写 2.5 / 2 / 1.5 / 2 与实现不符"的说法**已随这次重写消失**：现在以 `core/subtitle_limits.measure` 为准，改权重只需改那一处。改 `max_length` 或 `target_multiplier` 前先确认自己看的是**自动档位**还是**手动模式**（见 §六）。

另一个细节：`。`(U+3002)、`、`(U+3001) 落在 `0x3002`/`0x3001`，**不属于**任何判定区间（只覆盖 `0x3040-0x30FF` 假名与 `0xFF01-0xFF5E` 全角）→ 按 1 计权；而 `，`(U+FF0C) 属全角 → 1.75。

### 7.2 单行切分失败**不会**静默丢失（历史缺陷已修）

```python
# core/step5_splitforsub.py
with concurrent.futures.ThreadPoolExecutor(max_workers=load_key("max_workers")) as executor:
 # 必须消费 map 的返回值：executor.map 是惰性的，不迭代就不会取回结果，
 # 工作线程里的异常会被完全吞掉（见 devdocs 已知问题 P3-6）。
 list(executor.map(process, to_split))
```

- `executor.map` 返回的是**惰性迭代器**，历史上没有 `list` 它，于是 `process` 内抛出的异常不会冒泡（`Future` 的异常只在取结果时重抛），该行**保持未切分却没有任何日志**（历史缺陷 P3-6）。现在返回值被 `list` 消费，且 `process` 内部自带 `try/except`：出错时打印 `⚠️ 第 {i} 行切分失败（保留原行）: {类型}: {信息}` 并保留原始行。
- 保留原行的后果仍在：失败行不会被切开，三轮重试后可能写出**超过 `max_length` 的字幕行**——但现在**一定有日志**。排查方法是看控制台告警，或自己重算 `calc_len`（见第九节）。
- 仍然会触发失败的两类场景：① `align_subs` 里 `item[f'target_part_{i+1}']` 遇到 LLM 少返回一项 → `KeyError`；② `get_joiner(language)` 遇到两张语言表都不含的语言码（如 `th`）→ `ValueError`（`core/config_utils.py`）。

### 7.3 切分与时间轴之间的耦合

| 关系 | 事实 | 风险 |
| --- | --- | --- |
| 切分**不破坏**对齐 | `split_sentence` 只在**原字符串内部插入 `'\n'`**（`core/step3_2_splitbymeaning.py`），`align_subs` 返回 `src_part.split('\n')`（`core/step5_splitforsub.py`） | 拼接文本与切分前逐字符相同 → step6 的单调子串扫描仍能命中，这是「先 step5 再 step6」能工作的**根本前提**；一旦有人改成「改写句子再切分」，step6 立刻落到模糊兜底（`warn`）或抛 `ValueError`（`strict`） |
| 时间**只**来自 Source | `get_sentence_timestamps` 只用 `df_sentences['Source']`；`Translation` 不参与位置计算 | 译文长短、段数与源文不一致**不会**让时间轴错位，但会让「字幕内容与时间区间」语义错配（观众视角的错位） |
| 粒度变化必须**同时**重算 | step5 改变了行数，step6 依赖行数逐行生成时间 | 只重跑 step5 而 `translation_results_for_subtitles.xlsx` 与新 `translation_results.xlsx` 不匹配时，Source 序列对不上 → 大量单词兜底告警（`warn`）或 `ValueError`（`strict`）；两个 xlsx 必须来自同一次 step3/step4 |
| trim 在切分**之前** | `check_len_then_trim` 在 `core/step4_2_translate_all.py` 执行，step5 读的是 trim 后的译文 | 若把 trim 挪到 step5 之后，step5 的长度判定就会基于未裁剪的更长文本 → 字幕偏短/超长判断失真 |
| 词级数据换了就全盘错位 | `cleaned_chunks.xlsx` 若被重跑 step2 覆盖 | 词序列变化 → 老的行文本匹配不上 → 兜底告警铺满控制台（这是保护，不是静默错位） |

| `timestamp` 被就地改写成字符串 | | 之后任何想用 `timestamp` 做算术的代码都会失败；step4.2 之所以能 trim，是因为它读的是 `duration` 列（`core/step4_2_translate_all.py`） |
| 缝隙缝合只处理 <1 秒 | | `0 < delta_time < 1`：≥1 秒的静音段不会被覆盖，长静音处字幕会提前结束（设计如此） |
| 时间格式截断 | | `int(seconds * 1000) % 1000` 截断而非四舍五入，最多早 1ms；四舍五入会带来跨秒进位风险，截断是安全选择 |
| 无幂等 + 依赖桌面通知 | | 每次都覆盖 4 个 SRT；`send_notification` 走 `plyer`，无桌面环境（服务器/容器）会抛异常，但 已把该异常吞成一行黄字告警、不影响结果 |
| 中文句读与行尾标点 | | `for_display=True` 时：译文侧 `，`/`。` 换成空格**仅限非 CJK 目标语**（`polish_translation_for_display`；CJK 目标语保留句中逗号，否则分句会被空格粘成一串）；原文侧**默认保留**（`subtitle.strip_punctuation_in_source: true` 才把 `、。，！？` 也换成空格）；最后原文与译文的**行尾**句末标点一律由 `subtitle_split.strip_terminal_punctuation` 剥掉，句中与行首的标点保持原样 |
| 单列 SRT 的空行已修 | | 单列配置只写 `line1`（不再写空的第二行），块间恰好 1 个空行；`tests/` 里有对应回归 |

### 7.6 `json_to_subtitle.py` 的坑

- 无词级时间戳时用整段 `text` 兜底→ 该行 `text` 含空格，会让 step6 的位置映射失效（见 5.4 表格）。⚠️
- 不做去重、不做「超过 20 字符的 token 过滤」（whisperX 侧有：`core/all_whisper_methods/whisperX_utils.py`），也不做 `start <= end` 校验。
- 与 step6 重复实现了 `convert_to_srt_format`（两处若分别修改会产生格式分歧）。

### 7.7 2026-09-20/21 新增的三道闸门（对齐校验 / 轻改写 / 极短合并）

三条都是"用户实测发现问题 → 加闸门"的产物，改动前先读这一节，否则很容易误判成"代码多余"。

| 闸门 | 想解决的问题（实测） | 现在的做法 | 代价 / 注意 |
| --- | --- | --- | --- |
| **切点落在词中**（`subtitle.merge_broken_lines`） | 日语实测：step3_1 是**纯规则切分、没有提示词可管**，把 `…そのキャラクターやイラストの魅力を探り、フィギュアとし \| てその…` 从「として」中间劈开 → step4 只能把两个半句**各自翻译完整** → 出现"…同时注重这一点" / "同时也注重…" | 在 step3_1、step3_2 的**出口**用 spaCy token 边界校验（`subtitle_split.merge_broken_cuts` + `spaCy_boundaries`），坏切点就地并回相邻行 | 只有**新产出**的 `sentence_splitbynlp.txt` / `sentence_splitbymeaning.txt` 会过闸门；已有产物受幂等保护、不会被重写（要生效先删产物重跑） |
| **对齐结果不可用**（`subtitle.align_validate`） | 旧 `valid_align` 只检查「键存在 + `len(align) >= 2`」：段数与源文不符、空段、只剩一两个字的碎片都能直接落盘 | 段数必须等于源文段数 + 每段非空 + 无孤立碎片（`_MIN_PART_WIDTH = 6.0` 显示宽度）+ 段首不许是**悬空助词**（を/の/的，两种改写档都拦）；不通过就把**失败原因回注给模型**重试（`ask_gpt` 内 `max_retries = 3`）；仍不通过 → `split_text_evenly` **机械等分**（拼接必等于原译文，代价只是切点不如 LLM 精修） | 校验不通过会**多花 token**（同一 prompt 重试）；拦下次数与原因会在收尾的 `📊 对齐统计` 行里报出来 |
| **改写过度 / 全禁改写都不行**（`subtitle.align_allow_rewrite`） | 旧提示词笼统允许"适当改写" → 实测出现 `…程度 同时` + `同时也…`，观众连着两条读到两个"同时"；改成"一律不许改写"后又把顺句的小修（补连接词、补助词）一并禁掉，**切开的字幕读起来生硬**；而"让每行单独读起来是通顺的句子"同样有害 —— 它逼模型**补全裸从句**（凭空加主语/宾语/谓语，或把 part 1 的意思在 part 2 再说一遍） | **B 方案**：第 3 条拆成**两版**由本开关选择 —— 轻改写版（`_ALIGN_RULE3_LIGHT`，默认）只许"移动边界 / 移动一个虚词 / 删掉会孤零零留在切点上的连接词 / 最多补一个虚词"，并**明确禁止补全句子**；严格版（`_ALIGN_RULE3_STRICT`）一个字都不许动，但**两版都允许移动边界**（否则悬空切点无解）。校验同步分档，轻改写档拦五类结果 —— 段数 < 2 / 空段 / 孤立碎片、**段首悬空助词**（`dangling_start`）、长度比 `(0.8, 1.3)`、重复（`_adjacent_repeat` / `_inflated_ngram` / `_spurious_repeat`，用**计数对比**而不是"是否出现"，因此不会误伤原文本身就重复的句子）、覆盖率 < `REWRITE_COVERAGE_MIN = 0.85` | 开关**同时**切换提示词文本与校验严格度（判定点 `core/config_utils.align_allow_rewrite`），关掉它不会再出现"先改写一次 → 被拦 → 靠回注原因改回逐字切"的多余往返。设计约束：字幕是**跨条连读**的（用户 2026-09-20 原话"翻译字幕往往几句连起来看才是完整的句子"），所以第 7 条只要求每段**可解析**（不悬空、不切在短语中间），**不要求每行自足** —— 要求自足就会诱发跨行语义重复与凭空增补，这条不要在后续改动里撤掉 |

**收尾的对齐自检行**（`core/step5_splitforsub.py::align_stats_summary`，`split_for_sub_main` 里打印）：

```text
📊 对齐统计：LLM 对齐 N 行，其中轻改写 X 行 / 校验拦下 Y 次（带原因重试）/ 退回机械切分 Z 行
   原因示例：…（最多 3 条，取自被拦下时回注给模型的原因）
```

`X`/`Y`/`Z` 全为 0 时**整行不打印**（正常片子不该多出噪音）。要判断「允许轻改写」值不值，看这三个数在真实视频上的比例；要判断某一行为什么没切漂亮，看 `output/gpt_log/align_subs.json` 与 `output/gpt_log/error.json`。

**极短字幕合并**（`subtitle.merge_short_cues` + 两个阈值）的两条硬约束：合并后源/译**两侧**都不能超过 `上限 × GRACE`；两条字幕的**间隔**不能超过 `merge_max_gap`。都不满足就宁可保持"一闪而过"也不并（避免把不相关的话并到一起）。合并会把**行数改少**，因此源/译两列是成对删并的，step6 的行数随之变化——它读的就是合并后的 xlsx。

### 7.8 step5.2 字幕润色（2026-09-21 新增，可选步骤）

| 关系 / 坑 | 事实 | 风险 |
| --- | --- | --- |
| 为什么必须单独一步 | step5 的对齐**不许改写措辞**（§7.7 的 B 方案），而用户实测的"读起来断"（`作为自由原型师约6年，一直从事手办造型工作` 被切成两条）只能靠改措辞解决 | 把"改措辞"塞进 step5 的对齐提示词会与 B 方案的核心约束打架；反过来润色跑在 step5 **之后**，它看到的是**已切好的一条条 cue**，不是切分前的整句 |
| 只动 `Translation`，不动 `Source` | `polish_lines` 只替换译文列，`Source` 与行数逐行原样复制进 `OUTPUT_POLISHED_FILE`（`polish_subs_main` 用 `pd.DataFrame({'Source': …, 'Translation': polished})` 落盘） | 这正是它能插在 step6 之前的前提：step6 的位置匹配只用 `Source`，译文变长变短都不影响时间轴（见 §5.4） |
| 行数一致是**读表的前提** | `pick_translation_file()` 只在「开关打开 + 产物存在 + **行数与 step5 产物相等**」时返回润色表；产物缺失或读文件失败也退回原表 | 行数不同会让译文与时间轴整体错位，那种情况下**宁可放弃润色**（打印一行 ⚠️）。改 `BATCH_SIZE`、或给 `polish_lines` 加"合并/拆分行"之类的能力前，先确认"逐行对应"仍是它的出口不变量 |
| 机械护栏拦不住"换词式增补" | 覆盖率/长度/数字/重复四条都是**近似**判定（`POLISH_COVERAGE_MIN = 0.7` 本来就允许删虚词），模型把原行没有的意思补进去未必触发任何一条 | 所以才有 `get_polish_audit_prompt` 的批量审校（只审**改动过**的行）。**审校不可用时改动按原样保留**并计 `audit_failed`——这是刻意的取舍（少回退总好过因为审校不可用把改动全丢），别把它改成"审校失败就整批回退" |
| 失败只影响一批 | `polish_lines` 每批独立 try/except：该批保持原译文并计入 `failed_batches`，其余批次照常 | 绝不丢内容；重跑本步时命中的 (model, prompt) 缓存不再重复付费（按档位落在 `output/gpt_log/polish_subs.json` 或 `polish_subs_nothink.json`，缓存规则见 [`../03-subsystems/01-LLM调用与提示词.md`](../03-subsystems/01-LLM调用与提示词.md)） |
| 改开关**不会**自动重算 | 开关决定 step5.2 跑不跑、以及 step6 读哪张表；已写出的 `output/*.srt` 不会自己变 | 由关变开、由开变关，都要**重跑一次 step6**（不必重跑 step5/step5.2）；只有 step5 的产物变了才需要重跑 step5.2 |
| **关思考 = 更严门槛 + 更多回退** | `use_thinking=False` 时 `polish_lines` 把 `min_coverage` 从 `POLISH_COVERAGE_MIN = 0.70` 换成 `POLISH_COVERAGE_MIN_NO_THINKING = 0.85`（传给 `polish_ok`），因为关思考的模型会主动压缩、丢词（实测 `自由职业手办原型师` → `自由手办原型师`、`制作GK套件` → `做GK`） | 护栏拦下的行**保持原译文**，所以"关了思考却几乎没改动"是正常结果：先看 `✨ 润色统计` 的 `护栏拦下` 与 `拦下原因示例`。这个门槛是**自动收紧**的（按档位选常数），不要为了让改动率好看而把它改回 0.70 —— 0.70 拦不住关思考版的丢词 |
| 预筛只减少**送出的行**，不改产物行数 | `long_lines_only=True` 时 `stats['skipped']`（跳过）/ `stats['sent']`（送出）各记一笔，批次按 targets 切（跳过的行不占批），输出表仍与输入**逐行等长** | `skipped` 大、`改动` 少属正常（被跳过的行本来就顺）；判断"预筛是否砍掉了该润色的行"，看这两个数与 `✨ Polished sample` 对照表，别直接看 `改动` 的绝对值 |
| `extra_body` **本身不在缓存键里**，但 step5.2 给**润色**按档位分区 | 缓存命中只看 `(model, prompt)`（`core/ask_gpt.py::check_ask_gpt_history`），`extra_body` 既不参与匹配、也不写进日志条目 —— 所以 `polish_lines` 用 `_log_title(base, extra_body)` **把档位写进分区名**：润色开思考 → `output/gpt_log/polish_subs.json`，润色关思考 → `polish_subs_nothink.json`；审校不带 `extra_body`，两个档位都写 `polish_audit.json` | **切思考开关立即生效**（润色换到另一个分区，不会撞上另一档的旧响应，代价是两档各花一次钱）—— 这就是"改了开关却完全没变化"的处置从"删 `polish_subs.json`"变成"确认控制台那行 `🧠 润色思考：…` 就是你想要的档位"的原因。仍然需要删 json 的只剩一种情况：**提示词文本改了**（那才是同分区内换 `(model, prompt)`），此时润色两个分区文件 + `polish_audit.json` 都要删（`polish_subs*.json` + `polish_audit.json`）。反过来，同一档位重跑命中自己的分区时**不重复付费** |
| 仅转录模式自动跳过 | `polish_subs_main` 开头查 `transcription_only`：那种模式下译文就是原文，润色等于改写原文 | 该模式打开开关也不会有任何调用（只打印一行跳过） |

| `⚠️ 第 i 行 LLM 对齐不可用（…），已退回机械等分切分` | 该行的切点不是 LLM 精修的，但**拼接文本一定等于原译文**（不会丢内容） |
| `⚠️ 第 i 行切分失败（保留原行）` | 该行整行未切（见 §7.2） |

跑 step5.2（可选润色，`core/step5_2_polish_subs.py`）与随后的 step6 时：

| 输出 | 含义 |
| --- | --- |
| `✨ 字幕润色未开启（subtitle.polish_translation=false），跳过本步` | 开关关着 —— 本步零 LLM 调用（**正常**输出） |
| `✨ 当前是「只生成原语言字幕」模式，字幕润色跳过` | 仅转录模式自动跳过（译文就是原文，润色等于改写原文） |
| `🧠 润色思考：开（更忠实，约 20 行/批 2 万 tokens）／关（省约 91% token，覆盖率门槛自动提到 0.85）｜审校始终按默认档（思考开，约 860 tokens/次）` | 本次生效的思考档位（`subtitle.polish_thinking`）。**这行现在把"开关只管润色"写进去了**：括号里那半句是固定文案 —— 审校不跟随开关（约 860 tokens/次恒要花），所以"关思考"省的只是润色那部分；**关思考时覆盖率门槛自动是 0.85**，`护栏拦下` 会明显偏多 |
| `✂️ 润色范围：全部行` / `✂️ 润色范围：只润色有分句的长行` | 本次生效的润色范围（`subtitle.polish_long_lines_only`）。只有后者会打出非 0 的 `预筛跳过` |
| `✨ 润色统计：N 行（送出 X / 预筛跳过 Y）分 M 批，改动 A 行 / 护栏拦下 B 行 / 审校回退 C 行 / 失败 D 批｜思考 开/关` | 见 §5.2。`送出/预筛跳过` 只在开了"只润色有分句的长行"时才有意义（`Y` = 跳过没送的行）；**`改动 A` = 最终文本与原译文不同的行数**（用户肉眼所见的差异，由 `polish_lines` 末尾逐行比对得出，不是模型自报的标记），`审校回退 C` 只统计审校判为改信息的行 —— 两者独立、`C` 不会从 `A` 里扣减（回退的行文本=原译文，本来就不在 `A` 里）；`护栏拦下`/`审校回退` 占比高说明提示词与该语言不匹配（关思考时偏高是**预期**，见 §7.8）；`失败 D 批` > 0 表示有批次整批保持原译文（可重跑，命中缓存的批次不重复付费） |
| `✨ Polished sample（最多 5 行）` | Before / After 对照表，**只看得到改动过的行**；抽查它比逐行比对 xlsx 快 |
| `✨ 使用润色后的字幕表（subtitle.polish_translation 已开启）` | step6 真的读了润色表；若这里出现的是 `⚠️ 润色产物行数（…）与字幕表（…）不一致` 或 `没找到 …translation_results_polished.xlsx`，则用的是**未润色**表（需重跑 step5.2，或关掉开关） |

实测量级参考（2026-09-21 真实数据，只跑前 24 行 = 2 批、真实 LLM 调用，**当时的统计行还是旧文案，且 `改动` 还是旧口径**；新文案与新口径见上面的控制台表）：`✨ 润色统计：24 行分 2 批，改动 3 行 / 护栏拦下 0 行 / 审校回退 0 行 / 失败 0 批`（该次 `审校回退 0`，所以新旧口径同为 3 行 —— **有回退时两者才会分叉**，见下面的成本量级表）。改动都是措辞级的小修（`开始参加Wonder Festival。` → `并开始参加Wonder Festival。`、`现在也依然制作自己喜欢的作品` → `现在也依然在做自己喜欢的作品`、`由ALTER公司以成品手办形式发售。` → `由ALTER公司作为成品手办发售。`）。**改动比例低（3/24）是预期结果**：润色只顺措辞不重译，若某语言下改动比例明显更高，先怀疑提示词被改成了"重写/补全"。

**成本量级（2026-09-21 实测，`deepseek-flash`，用户自己的 79 行视频）** —— 两个取舍开关就是在这一组数字上定的：

| 档位 | 实测 token | 相对该片全流程 token |
| --- | --- | --- |
| 开思考，20 行/批 | prompt 1,208~1,268 + completion 3,983~19,397（其中 18,836 是 `reasoning_tokens`）≈ **20,600** tokens/批（可见输出只有 ≈ 560 tokens ≈ 1,300 字符的 JSON） | 全量 79 行 ≈ 4 批 ≈ **8.2 万 ≈ +30%** |
| 关思考，20 行/批 | prompt 1,220 + completion 568 = **1,788** tokens/批（**−91%，只算润色调用**） | — |
| 关思考 + 只润色有分句的长行 | 预筛跳过 24 行 → 3 批 ≈ 5.4 千 + 审校 ≈ 8 千 ≈ **1.3 万** | ≈ **+5%**（该次实测记录：改动 10 行 / 护栏拦下 2 行，覆盖率 83%、77%，都被收紧后的 0.85 门槛拦下 / 审校回退 6 行；用户人工确认 8 行读起来更顺且未丢信息）。⚠️ 其中 `改动 10` 是**旧口径**（当时 `changed` 计的是"送审 +1、回退 −1"的进审行数），按现在的口径 `改动` 直接从最终文本反推，那 6 行已被回退成原译文、不进 `改动`，同一次运行现在是 `改动 4 / 审校回退 6` |
| （同一次实测的另一条）40 行一批 vs 两个 20 行批 | 1,997 + 16,967 = 18,964 vs 25,856 → **−27%** | 说明 `BATCH_SIZE = 20` 本身也是成本旋钮；改它要同时确认"逐行对应"这个出口不变量（见 §7.8） |

> ⚠️ 上面三行的 **−91%** 只描述**润色调用**：审校调用 `_audit_info_changes` **不跟随**"允许模型思考"开关，恒按模型默认档（思考开）跑，所以它那一份开销在两档里都在（实测一次 3 行审校 ≈ 860 tokens/次；上表"关思考 + 预筛"那行的 ≈ 8 千就是该次全片审校的量级，不随开关变化）。

关思考 + 预筛这一次的改动样本（都是措辞级）：`借着在WF上结下的缘分` ← 去掉"上"；`另外虽然会比较简单，还会讲到…` ← 补"但"；`用心塑造插画中没画到的背后` ← "背后"改"背面"。

> ⚠️ **关思考的质量代价要一直记着**：关思考的模型压缩得更狠、会丢词（实测 `自由职业手办原型师` → `自由手办原型师`、`制作GK套件` → `做GK`），这正是覆盖率门槛自动收紧到 0.85 的原因，也是"回退比开思考多"的原因 —— 别把回退当成故障。

最小复现脚本（复刻 `get_sentence_timestamps` 的归一化逻辑，验证「句子 = 词串的单调子串」这一前提）：

```python
# 目录需为仓库根；需使用项目实际 Python 环境（带 pandas）
import pandas as pd, re

def norm(t):
 t = re.sub(r'\s+', ' ', str(t))
 t = re.sub(r'[^\w\s]', '', t)
 return t.strip

df = pd.read_excel('output/log/cleaned_chunks.xlsx')
df['text'] = df['text'].str.strip('"').str.strip
words = ''.join(norm(w.lower) for w in df['text'])

lines = [l.strip for l in open('output/log/sentence_splitbymeaning.txt', encoding='utf-8') if l.strip]
sent = ''.join(norm(l.lower).replace(' ', '') for l in lines)

print('words 长度 =', len(words), '| sentences 长度 =', len(sent))
print('完全一致 =', words == sent) # True 则 step6 必然走精确匹配路径
print('是否含空格 =', ' ' in words) # True 表示存在带空格的 token，5.3 的风险成立
```
