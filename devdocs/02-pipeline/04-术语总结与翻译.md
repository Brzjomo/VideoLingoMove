# step4：术语总结与翻译

## 一、职责与边界

step4 把 step3 切好的「句子级源文」变成「句子级译文」，并生成一份全局术语表供翻译时注入上下文。

- **负责**：① 汇总全文（前 N 字符）让 LLM 抽取主题与术语 → `output/log/terminology.json`（⚠️ 主题键名 `topic` vs `theme` 不一致，见 §4.1）；② 把句子切成 ~500 字符的块，多线程调用 LLM 两阶段翻译（faithful → expressive）；③ 把并发返回的译文按源文相似度回填到原 chunk 顺序；④ 复用 step6 的 `align_timestamp()` 给每句译文补上起止时间与 `duration`，并对超时长的句子做 trim；⑤ 产出 `output/log/translation_results.xlsx`。
- **不负责**：不做 ASR（step2）、不做句子切分（step3）、不做字幕二次切分与最终 SRT（step5/step6）、不做 TTS 时长估算的最终裁剪（step8 只提供被复用的 `check_len_then_trim()`）。
- `transcription_only=True` 时 step4 退化为直通模式：不调用 LLM，源文即译文，仍然产出 `translation_results.xlsx`（列比正常模式少）。

## 四、关键数据结构

### 4.1 `output/log/terminology.json`

```json
{
    "topic": "两句话的主题总结（见下方 ⚠️ 键名说明）",
    "terms": [
        { "src": "源语言术语", "tgt": "目标语言译法", "note": "简短解释" }
    ]
}
```

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `terms[].src` | str | LLM（`valid_summary` 强制要求存在，`core/step4_1_summarize.py:56`） | 术语原文，命中判定用小写子串匹配 |
| `terms[].tgt` | str | LLM / `custom_terms.xlsx` 第 2 列 | 目标语言译法 |
| `terms[].note` | str | LLM / `custom_terms.xlsx` 第 3 列 | 简短解释 |
| 顶层总结键 | str | LLM | ⚠️ **键名不一致**：prompt 要求输出 `topic`（`core/prompts_storage.py:75`），`valid_summary` 不校验该键，而 step4.2 读的是 `.get('theme')`（`core/step4_2_translate_all.py:98`）；`st.py:100` 在直通模式下手写的是 `{"theme": "", "terms": []}`。两侧键名不一致，正常模式下 `theme_prompt` 极可能为 `None`。⚠️ 需人工确认（取决于 LLM 实际返回的键） |

落盘：`json.dump(summary, f, ensure_ascii=False, indent=4)`（`core/step4_1_summarize.py:68-69`）；无幂等检查，每次调用都覆盖重写。

### 4.2 `output/log/translation_results.xlsx`

列名由 DataFrame 构造顺序决定，`index=False` 落盘：

| 运行模式 | 列顺序 | 列含义 |
| --- | --- | --- |
| 正常模式（`:144-152`） | `Source`, `Translation`, `timestamp`, `duration` | `timestamp` 是 **SRT 字符串**（如 `00:00:01,000 --> 00:00:02,500`，由 `align_timestamp` 在第 135 行转换）；`duration` 是 float 秒 |
| `transcription_only=True`（`:87-90`） | `Source`, `Translation` | **没有** `timestamp` / `duration` 列 |

> 注意：**不存在** `start` / `end` 独立列。`align_timestamp()` 内部先产生 `(start, end)` 元组与 `duration`（`core/step6_generate_final_timeline.py:125-126`），随后把 `timestamp` 列就地改写成 SRT 字符串（`:135`），所以 Excel 里只看得到合并后的 `timestamp`。

### 4.3 其它内存结构

| 名称 | 位置 | 结构 |
| --- | --- | --- |
| `chunks` | `core/step4_2_translate_all.py:96` | `list[str]`，每项是多行源文（行以 `\n` 分隔） |
| `results` | `:113-118` | `list[tuple[int, str, str]]` = `(chunk 下标, 源文, 译文)`，源文来自 `translate_lines()` 的第二个返回值 |

## 七、技术要点与坑

### 7.1 结果回填的对齐算法：并发 + 相似度匹配的隐式契约

回填代码（`core/step4_2_translate_all.py:121-139`）逐个 chunk 与**全部** results 做相似度比较：

```python
chunk_text = ''.join(chunk_lines).lower()
matching_results = [(r, similar(''.join(r[1].split('\n')).lower(), chunk_text)) for r in results]
best_match = max(matching_results, key=lambda x: x[1])
```

| 事实 | 依据 | 结论 |
| --- | --- | --- |
| `r[1]` 是该结果的**源文**，且 `translate_lines()` 的第二个返回值就是传入的 `lines` | `core/step4_2_translate_all.py:55`、`core/translate_once.py:67`/`:90` | 对「属于本 chunk 的那条结果」，`''.join(r[1].split('\n')).lower()` 与 `chunk_text` **逐字符相同**，`ratio()` 必然为 `1.0` |
| `max()` 取比值最大者，本 chunk 自己的结果必然在其中 | `:128-130`、`:114-115` | `best_match[1] < 0.9` 抛错分支（`:133-135`）与 `< 1.0` 告警分支（`:136-137`）**在现有代码路径下不可达**，属防御性代码；只有 `translate_lines` 的返回值语义被改动后才会生效 |
| `results.sort(key=lambda x: x[0])` | `:118` | **冗余**：回填按相似度在全量 results 中检索，不依赖顺序；`r[0]`（chunk 下标）在全流程中从未被读取，只是 `similar()` 之外的「备份键」 |
| 同一 `Source` 出现两次（重复句/重复 chunk） | `:130` `max()` 平局取**最先出现**的元素 | 两处都命中同一条结果 → 可能拿到「另一处」的译文；因为两条源文完全相同，不会抛异常、也拿不到告警，属**静默错配**（实践概率低） |
| 一个 future 抛异常 | `:114-115` `future.result()` 会重新抛出 | 异常在 `as_completed` 循环内直接向上传播，`results` 不完整 → `translate_all()` 整体失败；**不存在「部分失败仍继续回填」** |
| 回填后行数守恒 | `:139` `trans_text.extend(best_match[0][2].split('\n'))` + `translate_lines` 的行数校验（`:39`、`:86-88`） | `src_text` 与 `trans_text` 行数一致，`pd.DataFrame` 不会因长度不等而报错 |

> 💡 建议：如果要重构，直接 `results_by_index = {r[0]: r for r in results}` 按 `i` 取回即可，可省掉双重 `SequenceMatcher` 的 O(n²) 比较；保留相似度校验时，应把它改成「断言自匹配 ratio == 1.0」而不是用于选择。

### 7.2 `combine_chunks()` 的截断是刻意的取舍

`combined_text[:load_key('summary_length')]`（`core/step4_1_summarize.py:18`，带 `#!` 标记）只取**前 8000 个字符**（含 `' '.join` 补的空格）。

- 后果：长视频（例如 1 小时）的术语表**只覆盖开头部分**，后段专有名词不会被抽取；`custom_terms.xlsx` 是唯一的补充手段（会被无条件 `extend` 进 `terms`）。
- 后果：`' '.join(cleaned_sentences)` 用的是硬编码空格，而不是 `get_joiner(language)`，中文会被插入多余空格并占用字符预算——只是提示词层面的观感问题。
- 调大 `summary_length` 会线性增加 summary 请求的 token 成本。

### 7.3 术语注入点的隐性行为

| 现象 | 位置 | 说明 |
| --- | --- | --- |
| 子串匹配误命中 | `:24` | `term['src'].lower() in sentence.lower()` 是无边界子串匹配：术语 `AI` 会命中 `said`、`again`、`wait` 等词；中文短词（如「我」）命中面更大 |
| 序号不连续 | `:26-31` | 输出行的序号来自 `enumerate(things_to_note['terms'])`（**全量** terms），过滤后可能只剩 `3. "xxx"...` 这样的孤行 |
| 空术语表也注入标题 | `core/prompts_storage.py:46-50` | `custom_terms_json` 恒为**非空 dict**（即使 `terms` 为空列表，dict 仍为真值），所以 `### Existing Terms` 段总会出现在 prompt 里 |
| 重复术语 | `core/step4_1_summarize.py:66` | 「排除已有术语」只靠 prompt 约束，代码不查重；LLM 若忽略约束，`terms` 里会出现同 `src` 的多条，`search_things_to_note_in_prompt` 会重复输出 |
| `None` 被写进 prompt | `core/step4_2_translate_all.py:52-54` → `core/prompts_storage.py:112-126` | `previous_content_prompt`/`after_content_prompt`/`things_to_note_prompt` 为 `None` 时，f-string 会把它渲染成字面量 `None`（首/末块的 `<previous_content>` 段就是 `None`）。这是既有行为，不是异常 |

### 7.4 `pause_before_translate` 的人工介入点在 Streamlit 下会阻塞

```python
# st.py:108-109
if load_key("pause_before_translate"):
    input("⚠️ 翻译前暂停。请前往 `output/log/terminology.json` 编辑术语。完成后按回车继续...")
```

- `input()` 在 Streamlit 脚本线程中没有终端 stdin，默认 `false` 时不会走到；一旦置为 `true`，按钮点击的处理线程会**卡住**（无 stdin 时通常直接 `EOFError`/挂起），页面表现为「一直转圈」。⚠️ 需人工确认（取决于启动方式：`streamlit run` 无 tty，命令行 `python st.py` 才有 tty）。
- 安全做法：先在一个终端里跑 step4_1（或手动编辑 `output/log/terminology.json`），再在 `pause_before_translate: false` 下跑完整流程。

### 7.5 幂等性与缓存

| 机制 | 位置 | 影响 |
| --- | --- | --- |
| `translation_results.xlsx` 存在即跳过 | `core/step4_2_translate_all.py:64-66` | 想重跑必须**手动删除**该文件；`transcription_only` 模式下也走这条判断（`:64` 在 `:69` 之前） |
| `get_summary()` 无幂等判断 | `core/step4_1_summarize.py:36-71` | 可重复执行；但结果会被 `ask_gpt` 的缓存直接影响，见下一行 |
| `ask_gpt` 按 prompt 命中缓存 | `core/ask_gpt.py:34-45`、`:59-61` | 只要 `output/gpt_log/<log_title>.json` 中存在**完全相同**的 prompt，就直接返回历史响应、不发请求。改了 `terminology.json` 会改变 chunk prompt → 缓存自然失效；但改了 `custom_terms.xlsx` 而未清 `gpt_log/summary.json` 时，summary 会命中旧响应 |
| 重试靠追加空格绕过缓存 | `core/translate_once.py:36`、`:38` | `prompt + retry * " "`；日志仍追加到同一个 `translate_*.json`（`core/ask_gpt.py:25-32` 是 append 列表） |
| 校验失败落 `error.json` | `core/ask_gpt.py:98`、`:105` | 排查术语/翻译失败的第一现场 |

### 7.6 其它

- `max_workers: 1000` 会创建至多 `min(1000, len(chunks))` 个线程；chunk 数通常远小于 1000，实际并发≈chunk 数。用本地 LLM 时按注释改为 1。
- 正常模式**必然**依赖 `output/log/cleaned_chunks.xlsx`（`:142`）；直通模式也读它（`:83`）却不用——若只想跑字幕直通，必须先由 step2 生成该文件（或用 `core/json_to_subtitle.py` 生成）。
- 正常模式下 `align_timestamp` 会对**每一行** Source 做词级子串匹配，任一行匹配不上就抛 `ValueError`（`core/step6_generate_final_timeline.py:110`），这也是 step4 与 step3 切分结果的强耦合点（详见 `05-字幕切分与时间轴.md`）。
- 传 `subtitle_output_configs=[('trans_subs_for_audio.srt', ['Translation'])]` 但 `output_dir=None`（`:145-146`），因此该文件名只是占位、**不会**产生 `output/audio/trans_subs_for_audio.srt`。
