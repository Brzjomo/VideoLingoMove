#    pip install git-filter-repo

> 🔎 **G4 的教训**：P3-40 当初把这条记为"使用旧参数名，升级后需改"，Round 2 按建议直接改名——但**没有核对当前固定版本的签名**就改了。凡是"未来版本才需要"的改动，都必须先用 `inspect.signature()` 对着实际安装版本确认，否则就是把一个无害的弃用警告换成一个致命错误。
>
> 🔎 **G5 的教训**：`resolution=0x0` 同时承担了两个不相干的职责——"跳过压制以省时间"与"给纯音频输入造一个载体"。占位视频只对后者有意义；把它当成通用逻辑就会破坏前者。现在通过 `core/step1_ytdlp.is_audio_placeholder()` 显式区分这两种输入。

> 🔎 **这两个回归说明了一个值得记住的教训**：`save_subbtitles()` 里的副作用是**顺序敏感**的——"生成默认字幕"既是 zip 的来源、也是复制到输入目录的前提。重构时把副作用移除、却保留了依赖该副作用的守卫条件，是最容易漏的一类错误。现在函数开头的 docstring 已写明顺序要求。

### 5.2b 断句部分的 LLM 浪费与独立开关

| # | 位置 | 问题 | 处置 |
| --- | --- | --- | --- |
| **R16** | `core/step5_splitforsub.py` | **直通模式下的无谓自对齐**：`transcription_only=True` 时 `Source` 与 `Translation` 是同一份文本（`step4_2` 直通分支把源文复制给译文），但 `split_align_subs()` 仍会对每条超长字幕调 `align_subs()` —— 等于"让 LLM 把一段文本与它自己对- 齐"，结果必然等于输入。实测这段白花 **30 次调用** | 新增 `identical_src_trans = src_lines == tr_lines` 判断：文本相同时只调 LLM 切源文，译文用 `split_text_evenly()` 按行数机械等分（拼接回原文保真，已用 4 文本 × 4 分段验证）。step6 的对齐只需 Source 拼串精确匹配，等分不破坏它 |
| **R17** | `core/step3_2_splitbymeaning.py`、`core/step5_splitforsub.py` | **断句优化无法关闭**：`transcription_only` 只承诺跳过翻译，但 `step3_2`（按句意切分）与 `step5`（超长行切分）仍会调 LLM。用户"只要字幕"时这部分 token 无法省 | 新增配置 **`llm_sentence_split`** + 侧边栏开关「使用 LLM 优化断句」。**生效规则：翻译模式下强制开启（开关不显示），只有「只生成原语言字幕」时才允许关闭** （译文与源文长度差异大，不做按意群断句会影响双语对齐与单行长度达标）。关闭后 `step3_2` 直接输出 spaCy 结果、`step5` 用新增的 `split_by_punctuation()` 按标点就近断开，**整条链路零 LLM 调用**。判定与执行统一走 `core.config_utils.use_llm_sentence_split()` 单一入口，避免 UI 与代码漂移 |

**实测调用数对照**（同一份真实数据）：

| 模式 | step3_2 | step5-split | step5-align | 合计 |
| --- | --- | --- | --- | --- |
| 直通 + 断句优化开 | 25 | 67 | **0**（原为 30） | 92 |
| 直通 + 断句优化关 | 0 | 0 | 0 | **0** |
| 翻译 + 断句优化开 | 25 | 30 | 30 | 85 |
| 翻译 + 断句优化关 | 0 | 0 | 0 | **0** |

> `step5-align` 在"翻译"模式下是**必要的**（要按切分后的源文重新对齐译文），不可省；只在"直通"模式下才是浪费。
> `step5-split` 在直通模式下变成 67 是因为切分粒度变了（句子更短、更接近字面上限），这属于用 token 换断行质量，由 `llm_sentence_split` 控制。
