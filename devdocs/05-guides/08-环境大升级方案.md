> 全部改动在 `upgrade/env-torch28` 分支上，与 `merge/upstream-3.0.4` 隔离。
> 下文的"实测/已核实"是本次在你机器上用网络与 `nvidia-smi` 现场验证的结论；
> **第八节的 L0–L5 验收清单都还没执行**，落地后仍需逐级跑一遍。

## 一、为什么必须升级（强耦合，不是可选项）

whisperx 3.8.6 的依赖声明（PyPI 元数据实测）把整条链子锁死了：

| whisperx 3.8.6 的要求 | 含义 |
| --- | --- |
| `torch~=2.8.0`、`torchaudio~=2.8.0`、`torchvision~=0.23.0` | **想要 whisperx 3.8 就必须升 torch**；反之不升 whisperx 就可以不动 torch |
| `numpy>=2.1.0` | 必须升 numpy 2 |
| `ctranslate2>=4.5.0` | 必须升 ctranslate2（4.5 需要 cuDNN 9） |
| `pyannote-audio>=4.0.0` | 新增一大票传递依赖 |
| `torchcodec>=0.6.0,<0.8.0`（Windows 也包含） | 新增；它走 FFmpeg **共享库**解码，对 FFmpeg 版本有硬要求 |
| `huggingface-hub<1.0.0` | 与 `transformers>=5` 冲突（5 要求 hub>=1），所以 transformers 只能停在 4.x |
| `requires_python: >=3.10,<3.14` | Python 上限 3.13 |

**结论**：这次升级的核心决策其实是"要不要 whisperx 3.8"。要，就必须整套升；不要，就整套不动（现状 torch 2.1.2 + whisperx 3.2.0 + numpy 1.26 是自洽的）。

### 落地时用 PyPI 元数据核实/修正的几条

| 原方案的说法 | 核实结果 |
| --- | --- |
| `av` 17/18 在 Windows 只发 cp310/cp311，所以要选 3.11 | **不准确**。win_amd64 文件名确实没有 cp312/cp313，但有 **`cp311-abi3`（稳定 ABI，3.11+ 通用）**，所以 3.12/3.13 也能装；`av 18.x` 的 `requires_python` 是 `>=3.11`。默认仍取 3.11，但 3.12/3.13 不是"会被挡住" |
| numpy 只需 `>=2.1` | 需补上限。**numpy 2.5.x 起 `requires_python` 变成 `>=3.12`**，所以在 3.10/3.11 上会解析到更旧的版本。已钉 `>=2.1.0,<2.5.0` 统一两侧 |
| `demucs>=4.1` | PyPI 上最新就是 **4.1.0**（且它是首个提供 wheel 的版本）；声明 `torch>=2.1`、非 macOS-x86_64 平台 numpy 不受约束 → 与 2.8/2.x 兼容 |
| `pyannote-audio 4` 会带来一票传递依赖 | 核实：它自身就要求 `torch>=2.8.0` / `torchaudio>=2.8.0` / `torchcodec>=0.7.0`，与 whisperx 的 `torch~=2.8.0` 正好汇合 —— **torch 2.8 是下限而非上限** |
| `torchcodec>=0.6` | Windows 上 **只有 0.7.0 有 win_amd64 轮子**（0.6.0 一个都没有），所以实际必然落在 0.7.0 |
| `transformers` 只能停 4.x | 核实且确认互斥：whisperx 3.8.6 要求 `huggingface-hub<1.0.0`，transformers 5.x 要求 `huggingface-hub>=1.3.0` |

## 二、显卡架构矩阵（本次最关键的一条）

上游 3.x 默认用 **cu128**。但 PyTorch 在 **CUDA 12.8 / 12.9 构建里移除了 Maxwell / Pascal / Volta**（[pytorch#157517](https://github.com/pytorch/pytorch/issues/157517)），已有人在 sm_61 显卡上实测到 CUDA kernel 不支持。所以**不能一套 CUDA 版本打天下**：

| 显卡 | 算力 | 可用 torch 2.8 构建 | 说明 |
| --- | --- | --- | --- |
| **RTX 3080**（你的主力） | sm_86（Ampere） | **cu128（首选）/ cu126** | 完全支持。→ **按"直接升高版本"处理** |
| RTX 40 系（Ada） | sm_89 | cu128 / cu129 | 支持 |
| RTX 50 系（Blackwell） | sm_100/120 | **cu129**（cu128 亦可） | 需要新驱动 |
| Quadro P2200（本机） | sm_61（Pascal） | **只能 cu126** | cu128/cu129 构建已移除 Pascal |
| 无 N 卡 / macOS | — | `--index-url .../cpu` | CPU 版，转录很慢 |

**实测可用的自动识别方法**（不需要先装 torch）：

```bash
nvidia-smi --query-gpu=name,compute_cap --format=csv
# 本机实测输出： Quadro P2200, 6.1
```

据此实现了 `detect_torch_backend()`：`compute_cap < 7.0` → cu126；`>= 12.0` → cu129；其余 → cu128。
这样 3080 机器自动走 cu128（性能最好），而 P2200 那台机器自动回退到 cu126 仍可运行 ——
符合你"3080 能用就直接升，旧卡另外一套"的要求，且**不需要两套代码**。
（探测只依赖 `nvidia-smi --query-gpu=compute_cap`，不需要先装 torch；老驱动没有该字段时
回退到一张按型号匹配的算力表。）

### 已确认的 wheel 可用性（Windows x64，2026-09-18 复核）

| wheel 系列 | 结论 |
| --- | --- |
| `torch-2.8.0+cu126-*` / `+cu128-*` / **`+cu129-*`** | **三者都存在**，cp310/311/312/313 齐全 |
| `torchaudio-2.8.0+cu129-*` | 存在（cp310–cp313） |
| `torchvision-0.23.0+cu129-*` | 存在（cp310–cp313） |
| `torch-2.8.0+cu129-cp311-cp311-win_amd64.whl` | **3.57 GB**（`download.pytorch.org` HEAD 实测 200） |

> ✅ **原方案第十节里"cu129 的 torch 2.8.0 Windows wheel 是否存在（未确认）"已解除**：
> 存在，且 cp310–cp313 全有。
>
> ⚠️ 两点必须记住：
> 1. 这些带 `+cuXXX` 的 wheel **只在 `download.pytorch.org` 上**，PyPI 上的 `torch 2.8.0`
>    是不带本地版本号的另一套文件 —— 所以 `torch==2.8.0+cu129` 这种钉法在 PyPI 上必然失败，
>    必须配合 `--index-url`（`installer.py` 的 `TORCH_SPECS` 就是这么做的）。
> 2. 单个 torch wheel 就 2.7–3.6 GB，这是"必须先搬到大硬盘"的直接原因。

## 三、Python 版本选择：默认 **3.11**（3.10–3.13 均可用）

上游 `setup_env.py` 用的是 3.13。本项目默认取 3.11（最保守、轮子覆盖最确定），
但 3.10–3.13 都在支持范围内。逐版本的 wheel 覆盖实测：

| 包 | cp310 | cp311 | cp312 | cp313 |
| --- | --- | --- | --- | --- |
| `torch 2.8.0`（cu126/cu128/cu129） | ✅ | ✅ | ✅ | ✅ |
| `torchcodec 0.7.0` | ✅ | ✅ | ✅ | ✅（无 cp314） |
| `ctranslate2`（最新 4.8.2） | ✅ | ✅ | ✅ | ✅ |
| `numpy` | 2.2.6 封顶 | 2.4.6 封顶 | 2.5.x | 2.5.x |
| **`av`（faster-whisper 依赖）** | ✅ `cp310` | ✅ `cp311-abi3` | ✅ 走 abi3 | ✅ 走 abi3 |
| `spacy` 模型（`zh_core_web_md-3.8.0`） | `py3-none-any`，与 Python 版本无关 | | | |

> ⚠️ **原方案在 `av` 这一格上判断错了，这里更正。** 原文说"17.x/18.x 只发
> cp310/cp311，选 3.12/3.13 会回退到 av 16.1.0"——那是只看了文件名里的字面
> cp 标签。实际上 av 发的 `cp311-abi3` 是 **稳定 ABI（abi3）轮子，在 3.11 及
> 更新的 CPython 上都可安装**，所以 3.12/3.13 并不会被迫降级；
> `av 18.x` 的 `requires_python` 是 `>=3.11`（18.x 起连 cp310 都去掉了）。
> 结论不变（默认 3.11），但**理由要改**：选 3.11 是因为它是"所有依赖都确定
> 有对应轮子"的最保守选择，而不是因为 3.12/3.13 装不上。
>
> 💡 结论：默认 **3.11**；3.10–3.13 都在支持范围内（whisperx 3.8.6 的
> `requires_python` 是 `>=3.10,<3.14`）。`numpy` 的上限已按 Python 版本收紧为
> `<2.5.0`，保证 3.10/3.11 上不会解析出两套不同版本的环境。

## 四、目录布局：全部放进项目内（按你的要求）

目标：不占 C 盘、整个项目目录可搬移。做法是把**所有**缓存与虚拟环境都指向项目内：

```
<项目根>/
├── .venv/                    # uv 创建的虚拟环境（取代 conda videolingo）
├── _model_cache/             # 模型缓存（已是 config.yaml: model_dir 的默认值）
│   ├── models--Systran--faster-whisper-large-v3/   # HF 模型
│   ├── pyannote/                                    # 说话人/对齐模型
│   └── torch/                                       # torch.hub 缓存
├── .uv-cache/                # uv 下载缓存（可随时删）
├── .pip-cache/               # pip 下载缓存（可随时删）
├── ffmpeg/                   # 可选：installer.py 自动下载 7.x 到这里；
│                             #   放 ffmpeg.exe/ffprobe.exe 到 ffmpeg/bin/ 亦可，
│                             #   运行期由 runtime_libraries.py 自动接入
└── output/  history/  logs/  # 运行产物（已 gitignore）
```

对应的环境变量（由 `setup_env.py` 统一设置，避免"忘记设就写到 C 盘"）：

| 变量 | 指向 | 作用 |
| --- | --- | --- |
| `HF_HOME` | `<项目>/_model_cache` | HuggingFace 模型与 pyannote 权重 |
| `TORCH_HOME` | `<项目>/_model_cache/torch` | torch.hub 缓存（WhisperX 的 pyannote VAD 会读它） |
| `UV_CACHE_DIR` | `<项目>/.uv-cache` | uv 下载缓存 |
| `PIP_CACHE_DIR` | `<项目>/.pip-cache` | pip 下载缓存 |
| `HF_ENDPOINT` | 可选，如 `https://hf-mirror.com` | 国内下载加速（`setup_env.py --hf-mirror` 可设；不设时运行期仍走 dev 已有的 `check_hf_mirror()` 探测） |

> ⚠️ `_model_cache/` 会很大（whisper large-v3 约 3 GB，加对齐/VAD/Demucs 权重共 4–6 GB）。
> 搬移项目前先确认目标盘剩余空间 ≥ 20 GB（torch wheel 2.8–3.6 GB + 依赖约 2 GB + 模型 4–6 GB + 余量）。

## 五、要不要换 uv（回答你的问题）

**是，上游 3.x 已经从 conda 换成 uv**：`setup_env.py` 用 uv 在项目内建 `.venv`，Python 版本由 uv 自己下载，不再依赖 conda。

dev 升级前是三个启动脚本硬编码 conda：
`OneKeyStart.bat`、`batch/StartBatch.bat`、`AudioExtract/Start.bat` 都有
`call "%USERPROFILE%\anaconda3\Scripts\activate.bat" videolingo`。

**落地结果**：新增 `setup_env.py` 走 uv + 项目内 `.venv`；三个 `.bat` 改为**优先**用
`<项目>\.venv\Scripts\python.exe`，检测不到再回退 conda（保留兼容，不硬切）。
理由：uv 建环境快得多、能自己装 Python、且天然支持把缓存指到项目内；conda 的环境默认在
`C:\Users\...\anaconda3\envs\`，正是你不想占 C 盘的那部分。

> 未找到 uv 时 `setup_env.py` 会回退到标准库 `venv`（并明确警告：无法自选 Python 版本）。

## 六、执行步骤（搬到大硬盘后按序执行）

```bash

# 1) 安装 uv（若没有）
#    Windows: winget install --id=astral-sh.uv

# 2) 建项目内虚拟环境 + 装依赖（一条命令搞定：建 .venv、设缓存变量、调 installer）
#    加上 --smoke 会让装完的体检顺带逐个 import whisperx/torchcodec/pyannote
python setup_env.py --python 3.11 --smoke

#    想先看清楚会装什么（不改动任何东西；注意这一步用的是当前解释器，
#    只是确认"后端选择"是否符合预期，不会真的装）
python installer.py --dry-run

# 3) 装 spaCy 模型（3.8 系列；模型本身是 py3-none-any，与 Python 版本无关）
#    注意要用 .venv 里的解释器
.venv\Scripts\python.exe -m spacy download zh_core_web_md
.venv\Scripts\python.exe -m spacy download en_core_web_md
#   （其余语种按 config.yaml 的 spacy_model_map 需要再装）

# 4) 体检（--smoke 会把 whisperx/torchcodec/pyannote 等逐个 import 一遍）
python installer.py --check --smoke

# 5) 单元测试
python -m unittest discover -s tests -v

# 6) 启动
.venv\Scripts\python.exe launch.py
```

### 落地时偏离原方案的两个决定

**1. FFmpeg 下载链接不能写死（原方案说"改为固定 7.x"）**

实测 BtbN/FFmpeg-Builds 的 release 结构：
- 长期 tag 只有 `latest`，而且**会被覆盖** —— 现在 `latest` 下只剩 `master`（8.1/9.0）与 `n8.1`/`n9.0`，**7.x 资产已经不在里面了**；
- `7.1` / `7.0.2` 这类 tag **从来不存在**（原方案给的 URL 形式 404）；
- 带 7.1 资产的只有 autobuild tag（如 `autobuild-2026-07-31-14-10` 下的
  `ffmpeg-n7.1.5-12-g1fdbca85aa-win64-gpl-7.1.zip`，实测 200 / 151 MB），
  而 autobuild 会被 GitHub 定期清理。

所以无法给出一个"现在有效、将来也有效"的静态链接。改为 `resolve_ffmpeg_url()`：
安装时查 GitHub Releases API（先 `latest`，再最近 30 个 release），按前缀
`ffmpeg-n7.1` + `win64-gpl` + **排除 `-shared`**（shared 版只有 DLL、没有
`ffmpeg.exe`）挑一个资产；离线/内网可用 `VIDELINGO_FFMPEG_URL` 覆盖；都失败时
给出手动放置 `ffmpeg\bin\` 的指引。**本机已有系统 FFmpeg 7.0.2，不会走下载分支。**

**2. `torch.load` 垫片的位置**

原方案把它放在 `torch` 导入之后即可；实际实现把它提到 `import torch` 与
`import whisperx` 之间，确保 whisperx（以及它在 import 期引入的
`pyannote.audio`）**任何一次** `torch.load` 调用都在垫片生效之后。

### 已核实"不需要改"的（原判断仍然成立）

| 项 | 依据 |
| --- | --- |
| numpy 2 兼容 | 全仓 grep `np.float/np.int/np.bool/np.NaN/np.Inf` 等 2.0 已移除别名 → **0 命中** |
| `librosa` 1.x 兼容 | 唯一剩余用法是 `core/step2_whisperX.py` 里 `librosa.load(path, sr=16000)`（仅作回退），该签名在 1.x 仍在 |
| spaCy 模型与 Python 版本绑定 | `zh_core_web_md-3.8.0` / `en_core_web_md-3.8.0` 都是 `py3-none-any`，只需 spacy 3.8.x 匹配 |
| `whisperx.load_model()` 的 `vad_options` / `download_root` 参数 | **已核实** 3.8.6 的 `load_model()` 签名（见 v3.8.6 `whisperx/asr.py`）仍含 `vad_options`、`download_root`、`asr_options`，dev 现有调用无需改参数名；`whisperx.align()` 同样仍接受 `return_char_alignments` |
| VAD 模型是否需要联网下载 | **不需要**：3.8.6 的 `load_vad_model()` 从 whisperx 包内自带的 `whisperx/assets/pytorch_model.bin` 加载，不请求 HuggingFace。这也是第 2 条垫片必要的原因（该 checkpoint 用 `torch.load` 读） |

## 九、回滚方案

```bash
git checkout merge/upstream-3.0.4      # 回到已验证的合并分支（本次升级单独在 upgrade/env-torch28）
# 环境侧：删掉项目内 .venv / .uv-cache / .pip-cache 即可；conda 的 videolingo 环境未被触碰
```

- 升级改动**全部在 `upgrade/env-torch28` 分支**上，与 `merge/upstream-3.0.4` 隔离，随时可弃。
- `requirements.txt` 是唯一"改了就会影响安装结果"的声明文件；若安装失败，先
  `git checkout merge/upstream-3.0.4 -- requirements.txt` 回到旧栈（注意：旧栈的
  `torch 2.1.2` 由旧 `installer.py` 安装，回滚 `requirements.txt` 时最好一并回滚
  `installer.py`）。
- 模型与缓存都在项目内，删目录即回滚，不污染系统；系统级只可能多出一个
  `ffmpeg/` 目录（同样在项目内）。
- ⚠️ 新栈落地后**模型的 ONNX/权重缓存可能要重下**：`_model_cache/` 里旧栈留下的
  faster-whisper 与对齐模型在新版 `ctranslate2`/`transformers` 下仍可读取，但
  若报版本不匹配，删掉对应子目录让它重下即可。

## 十、风险与未验证项（如实记录）

| 项 | 状态 |
| --- | --- |
| cu129 的 torch 2.8.0 Windows wheel 是否存在 | ✅ **已确认存在**（cp310–cp313，`download.pytorch.org` 实测 200，约 3.57 GB）；注意它**不在 PyPI 上** |
| `av` 在 Windows 上对 3.12/3.13 的可得性 | ✅ **已确认**：`cp311-abi3` 是稳定 ABI 轮子，3.11+ 通用；原方案"3.12/3.13 会回退到 av 16.1.0"的说法**不成立** |
| numpy 的上限 | ✅ 已按 Python 版本收紧到 `<2.5.0`（2.5.x 起要求 Python ≥3.12，会让 3.10/3.11 解析到不同版本） |
| `whisperx.load_model()` / `align()` 的 API 兼容性 | ✅ **已核实**（读 v3.8.6 源码）：`load_model()` 仍有 `vad_options`/`download_root`/`asr_options`，`align()` 仍有 `return_char_alignments`，dev 现有调用无需改签名 |
| 原方案给的 FFmpeg 固定下载链接 | ❌ **实测 404**：`7.1`/`7.0.2` tag 不存在，`latest` 下的 7.x 资产已被覆盖。已改为运行时查 API（见第七节） |
| `torchcodec` 在本机 FFmpeg 7.0.2 上能否正常解码 | **未验证**（没装环境）。大版本在支持区间（4–7）内，Windows 上还依赖 `os.add_dll_directory()` 注入；`torchcodec.decoders` 也已纳入 L1 冒烟 |
| `torch.load` 垫片的真实必要性 | **半验证**：垫片本身有单元测试锁语义，但"不打垫片就会失败"只在源码层面成立（pyannote checkpoint 含 omegaconf 对象 + torch≥2.6 默认 `weights_only=True`）。装完环境后建议实测一次 |
| pyannote-audio 4 是否额外要求 HuggingFace 授权/令牌 | **未验证**。WhisperX 默认只用其 VAD（3.8.6 从包内自带权重加载，不联网），说话人分离才需要；若报下载鉴权错误需申请模型许可 |
| RTX 3080 实机验证 | **未做**（本机是 P2200）。3080 属 sm_86，cu128 官方支持，但仍需按 L0b/L4 实测 |
| 磁盘空间 | ✅ 已解决：项目现在在 `E:\VideoLingoMove`，`F:` 盘另有约 3.5 TB 空闲；E 盘只剩约 100 GB 总容量的余量，装完 `.venv` + 模型后需留意 |
| 无依赖环境下的 `installer.py --check` | 只验证了"会正确报错并返回非零码"（本机 base Python 没装 torch/whisperx，符合预期）；**通过路径未验证** |
