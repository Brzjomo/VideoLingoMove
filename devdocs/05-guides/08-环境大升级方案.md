# 环境大升级方案

> **本文档是待执行方案，不是已完成的记录。** 代码/配置改动与安装验证都还没做；
> 计划是先把项目整体搬到有空间的硬盘，再按本文执行安装与验证。
> 本文所有"实测/已核实"的结论都是本次在你机器上用网络与 `nvidia-smi` 现场验证的，
> 不是照抄上游；标注"未验证"的部分请勿当成结论。

## 一、为什么必须升级（强耦合，不是可选项）

whisperx 3.8.6 的依赖声明（PyPI 元数据实测）把整条链子锁死了：

| whisperx 3.8.6 的要求 | 含义 |
| --- | --- |
| `torch~=2.8.0`、`torchaudio~=2.8.0`、`torchvision~=0.23.0` | **想要 whisperx 3.8 就必须升 torch**；反之不升 whisperx 就可以不动 torch |
| `numpy>=2.1.0` | 必须升 numpy 2 |
| `ctranslate2>=4.5.0` | 必须升 ctranslate2（4.5 需要 cuDNN 9） |
| `pyannote-audio>=4.0.0` | 新增一大票传递依赖 |
| `torchcodec>=0.6.0,<0.8.0`（Windows 也包含） | 新增；它走 FFmpeg **共享库**解码，对 FFmpeg 版本有硬要求 |
| `huggingface-hub<1.0.0` | 与 `transformers>=5` 冲突（5 要求 hub>=1），所以 transformers 只能停在 4.x |
| `requires_python: >=3.10,<3.14` | Python 上限 3.13 |

**结论**：这次升级的核心决策其实是"要不要 whisperx 3.8"。要，就必须整套升；不要，就整套不动（现状 torch 2.1.2 + whisperx 3.2.0 + numpy 1.26 是自洽的）。

## 二、显卡架构矩阵（本次最关键的一条）

上游 3.x 默认用 **cu128**。但 PyTorch 在 **CUDA 12.8 / 12.9 构建里移除了 Maxwell / Pascal / Volta**（[pytorch#157517](https://github.com/pytorch/pytorch/issues/157517)），已有人在 sm_61 显卡上实测到 CUDA kernel 不支持。所以**不能一套 CUDA 版本打天下**：

| 显卡 | 算力 | 可用 torch 2.8 构建 | 说明 |
| --- | --- | --- | --- |
| **RTX 3080**（你的主力） | sm_86（Ampere） | **cu128（首选）/ cu126** | 完全支持。→ **按"直接升高版本"处理** |
| RTX 40 系（Ada） | sm_89 | cu128 / cu129 | 支持 |
| RTX 50 系（Blackwell） | sm_100/120 | **cu129**（cu128 亦可） | 需要新驱动 |
| Quadro P2200（本机） | sm_61（Pascal） | **只能 cu126** | cu128/cu129 构建已移除 Pascal |
| 无 N 卡 / macOS | — | `--index-url .../cpu` | CPU 版，转录很慢 |

**实测可用的自动识别方法**（不需要先装 torch）：

```bash
nvidia-smi --query-gpu=name,compute_cap --format=csv
# 本机实测输出： Quadro P2200, 6.1
```

据此写一个 `detect_torch_index()`：`compute_cap < 7.0` → cu126；`>= 12.0` → cu129；其余 → cu128。
这样 3080 机器自动走 cu128（性能最好），而 P2200 那台机器自动回退到 cu126 仍可运行 ——
符合你"3080 能用就直接升，旧卡另外一套"的要求，且**不需要两套代码**。

### 实测确认的 wheel 可用性（Windows x64）

| wheel | HTTP 状态 | 大小 |
| --- | --- | --- |
| `torch-2.8.0+cu126-cp311-cp311-win_amd64.whl` | 200 | **2780 MB** |
| `torch-2.8.0+cu128-cp311-cp311-win_amd64.whl` | 200 | **3301 MB** |
| `torch-2.8.0+cu129-*` | 请求报错（未确认，需再验） | — |

> ⚠️ 单个 torch wheel 就 2.7–3.3 GB，这是下面"必须先搬到大硬盘"的直接原因。

## 三、Python 版本选择：建议 **3.11**

上游 `setup_env.py` 用的是 3.13。但对 **Windows** 来说 3.11 的轮子覆盖最稳，实测数据：

| 包 | cp310 | cp311 | cp312 | cp313 |
| --- | --- | --- | --- | --- |
| `torch 2.8.0`（cu126/cu128） | ✅ | ✅ | ✅ | ✅ |
| `ctranslate2`（最新 4.8.2） | ✅ | ✅ | ✅ | ✅ |
| `torchcodec 0.7.0` | ✅ | ✅ | ✅ | ✅（无 cp314） |
| **`av`（faster-whisper 依赖）** | ✅ | ✅ | ❌ | ❌ |
| `spacy` 模型（`zh_core_web_md-3.8.0`） | `py3-none-any`，与 Python 版本无关 | | | |

`av` 是关键：**17.x / 18.x 在 Windows 上只发 cp310/cp311（+cp314），没有 cp312/cp313 轮子**，只有 `av 16.1.0` 覆盖到 cp313。选 3.12/3.13 时 pip 会自行回退到 av 16.1.0（能用，但版本偏旧）；选 **3.11 则可直接用最新 av**。

> 💡 结论：默认 **3.11**；想跟上游就 3.13，但要接受 `av` 回退。本文其余命令以 3.11 为例。

## 四、目录布局：全部放进项目内（按你的要求）

目标：不占 C 盘、整个项目目录可搬移。做法是把**所有**缓存与虚拟环境都指向项目内：

```
<项目根>/
├── .venv/                    # uv 创建的虚拟环境（取代 conda videolingo）
├── _model_cache/             # 模型缓存（已是 config.yaml: model_dir 的默认值）
│   ├── models--Systran--faster-whisper-large-v3/   # HF 模型
│   ├── pyannote/                                    # 说话人/对齐模型
│   └── torch/                                       # torch.hub 缓存
├── .uv-cache/                # uv 下载缓存（可随时删）
├── .pip-cache/               # pip 下载缓存（可随时删）
├── ffmpeg/                   # 可选：把 ffmpeg.exe/ffprobe.exe 放这里，避免依赖系统 PATH
└── output/  history/  logs/  # 运行产物（已 gitignore）
```

对应的环境变量（由 `setup_env.py` / 启动脚本统一设置，避免"忘记设就写到 C 盘"）：

| 变量 | 指向 | 作用 |
| --- | --- | --- |
| `HF_HOME` | `<项目>/_model_cache` | HuggingFace 模型与 pyannote 权重 |
| `TORCH_HOME` | `<项目>/_model_cache/torch` | torch.hub 缓存 |
| `UV_CACHE_DIR` | `<项目>/.uv-cache` | uv 下载缓存 |
| `PIP_CACHE_DIR` | `<项目>/.pip-cache` | pip 下载缓存（若仍用 pip） |
| `HF_ENDPOINT` | 可选，如 `https://hf-mirror.com` | 国内下载加速（dev 已有 `check_hf_mirror()` 逻辑） |

> ⚠️ `_model_cache/` 会很大（whisper large-v3 约 3 GB，加对齐/VAD/Demucs 权重共 4–6 GB）。
> 搬移项目前先确认目标盘剩余空间 ≥ 20 GB（torch wheel 2.8 GB + 依赖约 2 GB + 模型 4–6 GB + 余量）。

## 五、要不要换 uv（回答你的问题）

**是，上游 3.x 已经从 conda 换成 uv**：`setup_env.py` 用 uv 在项目内建 `.venv`（或 `~/.venvs/videolingo` 共享环境），Python 版本由 uv 自己下载，不再依赖 conda。

dev 现状是三个启动脚本硬编码 conda：
`OneKeyStart.bat`、`batch/StartBatch.bat`、`AudioExtract/Start.bat` 都有
`call "%USERPROFILE%\anaconda3\Scripts\activate.bat" videolingo`。

**建议方案**：新写 `setup_env.py` 走 uv + 项目内 `.venv`，三个 `.bat` 改为优先用 `<项目>\.venv\Scripts\python.exe`，检测不到再回退 conda（保留兼容，不硬切）。
理由：uv 建环境快得多、能自己装 Python、且天然支持把缓存指到项目内；conda 的环境默认在 `C:\Users\...\anaconda3\envs\`，正是你不想占 C 盘的那部分。

## 六、执行步骤（搬到大硬盘后按序执行）

```bash
# 0) 前置检查：目标盘剩余空间 ≥ 20 GB；ffmpeg/ffprobe 在 PATH 且大版本为 4–7
ffmpeg -version

# 1) 安装 uv（若没有）
#    Windows: winget install --id=astral-sh.uv  或  powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

# 2) 建项目内虚拟环境（不碰 conda、不写 C 盘）
python setup_env.py --python 3.11 --path .

# 3) 装依赖（setup_env.py 内部会调用 installer.py，并自动选择 CUDA 轮子）
python installer.py --torch-backend auto --check    # 先干跑体检，确认选中的是 cu128
python installer.py --torch-backend auto            # 真正安装

# 4) 装 spaCy 模型（3.8 系列；模型本身是 py3-none-any，与 Python 版本无关）
python -m spacy download zh_core_web_md
python -m spacy download en_core_web_md
#   （其余语种按 config.yaml 的 spacy_model_map 需要再装）

# 5) 体检 + 单元测试
python installer.py --check
python -m unittest discover -s tests -v

# 6) 启动
python launch.py
```

| 级别 | 做什么 | 通过标准 |
| --- | --- | --- |
| L0 | `python installer.py --check` | 退出码 0；Python/关键包/torch·torchaudio 同源/ffmpeg·ffprobe/CJK 字体/config 全部通过 |
| L0b | 打印选中的 CUDA 后端与 GPU 信息 | 3080 机器显示 **cu128**；`torch.cuda.is_available()` 为 True，`torch.cuda.get_device_name(0)` 正确 |
| L0c | `python -m unittest discover -s tests -v` | 46 例全绿（不依赖新栈，但能挡住明显回归） |
| L1 | 逐个 import 冒烟：`whisperx`、`torchcodec.decoders`、`pyannote.audio`、`ctranslate2`、`faster_whisper`、`demucs.api`、`spacy`、`streamlit` | 全部成功；**`torchcodec.decoders` 是 Windows 上最容易失败的一个**（FFmpeg 共享库/DLL 目录） |
| L2 | 单步跑通：`python -m core.step1_ytdlp`（或直接放一个短视频到 `output/`）→ `python -m core.step2_whisperX` | 产出 `output/log/cleaned_chunks.xlsx`；控制台无 traceback |

| L5 | 缓存与可搬移性 | 跑完后确认 `_model_cache/`、`.venv/`、`.uv-cache/` 都在项目内；`C:\Users\<你>\.cache\huggingface` **没有**新增内容 |

## 九、回滚方案

```bash
git checkout merge/upstream-3.0.4      # 回到已验证的合并分支（本次升级单独在 upgrade/env-torch28）
# 环境侧：删掉项目内 .venv/.uv-cache 即可，conda 的 videolingo 环境未被触碰（如果还在）
```

- 升级改动**全部在 `upgrade/env-torch28` 分支**上，与 `merge/upstream-3.0.4` 隔离，随时可弃。
- `requirements.txt` 是唯一"改了就会影响安装结果"的文件；若安装失败，先 `git checkout merge/upstream-3.0.4 -- requirements.txt` 回到旧栈。
- 模型与缓存都在项目内，删目录即回滚，不污染系统。
